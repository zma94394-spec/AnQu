### 关键技术决策（后续改动需保持一致）
1. **分类用字典表，平台/状态用 ENUM**：分类可能随版本新增，ENUM 加值在事务中受限。
2. **计数列反范式冗余 + 触发器同步**：读远多于写，列表排序需命中索引。
3. **RLS 必须配合列级 GRANT**：RLS 只管行不管列，否则作者可自行刷高 likes_count。
4. **SQL 脚本是 DDL 唯一真源**，禁止 `prisma migrate dev`（会与 RLS/触发器/生成列冲突），
   结构变更后跑 `prisma db pull` 对齐。
5. **点赞双路径**：登录走 `toggle_build_like`（幂等，基于 build_likes 表）；
   匿名走 `increment_build_likes`（不去重）。
6. **Prisma 直连调用依赖 `auth.uid()` 的 RPC 时，必须在同一事务内
   `set_config('request.jwt.claims', ..., true)`** 注入声明，否则 auth.uid() 返回 NULL。
   这一点容易遗漏，已写入 `builds.service.ts` 注释。

### 排序语义（前端与后端需对齐）
`latest` / `hot`(点赞×3+复制，按小时龄 0.6 次幂衰减) /
`cost_performance`((点赞×2+复制)/造价×10000) / `cost_asc` / `cost_desc`。

## 第四轮：修正「排序无法命中索引」的错误结论

### 背景
README 与历次回复中都笼统写着「热度/性价比排序无法命中索引」。本轮用探针实测后
发现该结论**对性价比一项是错的**。

### 实测结论（PGlite 上直接尝试建表达式索引）
| 函数 | `provolatile` | 建表达式索引 |
|---|---|---|
| `build_cp_score` | `i` (IMMUTABLE) | ✅ 成功 |
| `build_hot_score` | `s` (STABLE) | ❌ 被拒：`functions in index expression must be marked IMMUTABLE` |

**根因**：索引表达式只接受 `IMMUTABLE` 函数；`build_hot_score` 依赖 `now()`，
只能标 `STABLE`。这是结构性限制，调优无法绕过。

### 落地的改动
1. `tests/integration.test.mjs` 新增「索引可行性」断言（正向建 cp 索引 + 反向断言
   hot 被拒），把这条架构约束固化为回归测试。测试数 33 → **34**。
2. README 第 7 节第 2 条改写为三行表格，并给出 `ix_builds_cp_score` 的候选索引 DDL：
   列顺序对齐 `ORDER BY cp_score DESC, b.id DESC`，`WHERE status='published'`
   对齐 `buildWhere()` 的恒定条件，构成**部分表达式索引**。
   ⚠️ 已标注：能建 ≠ 该建，写放大代价需先 `EXPLAIN ANALYZE` 确认。
3. 技能 `pg-schema-verification` 补入第 9 项必测断言「索引可行性」及实测手法。

### 交付

- `web/src/lib/validation.ts` —— 逐条镜像后端 `createBuildBodySchema` 的校验规则。
- `web/scripts/check-validation-parity.mts` —— **前后端校验一致性检查**（34 个边界用例）。
- `App.tsx` 接线：发布成功后 reload，并判断新方案是否被当前筛选过滤掉后给出说明 + 一键清空筛选。

### 关键决策
1. **发布弹窗由父组件条件渲染**，不传 `open` prop —— 每次打开都是全新挂载，
   表单状态天然重置，省掉一整套 reset 逻辑。
2. **枪械选择器用「按钮展开面板」而非 combobox** —— combobox 要同时管理
   「输入的是搜索词还是已选值」，边界情况多；面板式语义明确、键盘可达。
3. **状态更新不写在 setState 的更新函数里**：React 严格模式下更新函数会执行两次，
   在里面调 setErrors 不可靠。改为用闭包里的 values 直接算新值。

### ⚠️ 一致性检查抓到的 2 个真实缺陷（务必保留该脚本）
都是**静默归一化**造成的，属"看起来没问题、实际会写脏数据"的类型：

| 缺陷 | 根因 | 修复 |
|---|---|---|
| 造价为空被转成 `0` | `Number('')` 在 JS 里 === `0`，于是"没填造价"变成"造价 0 柯恩币" | `toCreateBuildInput` 未填时**整体省略该字段**，让后端 `required_error` 正常触发；`CreateBuildInput.estimated_cost` 改为可选 |
| 空标签被 `.filter()` 掉 | 前端拦下、后端其实也会拦（`z.string().trim().min(1)`），形成假分歧，且静默丢弃用户输入 | 不再过滤，原样传递交后端判定 |

**通用教训**：校验层与转换层都不要做静默归一化 —— 要么原样传递让下游判定，
要么显式省略字段表达"未提供"，绝不要把非法值悄悄换成另一个合法值。

- 新增 `hooks/useCopyCode.ts`、`hooks/useLikeBuild.ts` —— 把卡片与详情页共用的交互抽成 hook。
- 新增 `lib/queryParams.ts`、`lib/appShell.ts`。
- 新增 `scripts/check-mocks.mts`（`npm run check:mocks`）。

### 关键技术决策
1. **列表筛选状态全部迁到 URL search params**。理由：分享站用户会把筛选后的链接发给队友；
   前进后退可用；Header 搜索框在详情页也能用（跳 `/?q=`），不必给每个页面单独接线。
   约定**默认值不写入 URL**；筛选变更用 `replace`，**翻页用 push**。
2. **详情页主体必须拆成内层组件** —— `useCopyCode`/`useLikeBuild` 依赖已加载数据，
   而 hooks 不能写在 `build === null` 的条件分支里。父组件在数据就绪后才渲染内层组件。
3. **复制/点赞逻辑抽成 hook**：这段逻辑有三处不显眼但必须一致的细节
   （剪贴板降级、计数上报失败不回滚成功态、2s 复位且卸载清定时器），
   任一在某个副本里漏掉就会出现"卡片上能复制、详情页上不能"这类难查问题。
4. **`AUTH_REQUIRED` 必须与普通失败区别对待**：`POST /comments` 挂了 `requireAuth`，
   未登录是"缺前置条件"而非"出错了"，提示"重试"毫无意义。
5. **Mock 数据加一致性自检**：评论数徽标从评论数据推导（不手写），
   并在模块末尾断言两者一致 —— 否则"卡片显示 2 条、详情页只有 1 条"会让用户觉得站点是坏的。

### 踩坑记录
- **移动代码块时用了错误的锚点顺序**：用 python 脚本移动 `seed.ts` 的评论块时，
  目标锚点 `组装` 在源块**之前**，导致 `s[i:j]` 取到空串、`s[:i]+s[j:]` 把中间区域复制了一份，
  文件被写坏（`MOCK_BUILDS` 出现两次）。**教训：切片移动前先断言 `i < j`**。
  由于 Write 工具要求先 Read 才能覆盖，最终用 `rm` 后重写解决。
- **`hot_score` 不能做精确相等比较**：`hotScore()` 读 `Date.now()`，
  模块加载时组装一次、检查时重算一次，相隔几毫秒分数就有极小差异 → 断言必然随机失败。
  已改为相对容差（1e-3）。`cp_score` 不含时间项，可精确比较。
- **`React.ReactNode` 等 UMD 全局类型在 `verbatimModuleSyntax` 下不报错但不可靠**，
  已统一改为 `import type { ReactNode } from 'react'`。

### ⚠️ 用户提供的部署参数中发现的 4 处问题（均已修正并写入 DEPLOY.md）
1. **SQL 顺序错误**：用户给的是 `01→02→03→04`，正确是 **`01→03→02→04`**。
   `02_rls.sql` 引用了 `03_functions.sql` 的 4 个函数共 10 处
   （`is_staff()` ×7、`increment_build_copies`、`increment_build_likes`、`toggle_build_like`）。
   按用户顺序执行会在第二个文件报 `function public.is_staff() does not exist`，
   且因策略逐条创建会留下"半套 RLS"，比彻底失败更难排查。
2. **缺 `SUPABASE_ANON_KEY`**：`src/lib/env.ts` 里是**必填**，缺了进程直接 `process.exit(1)`。
3. **缺 `CORS_ORIGIN`**：默认值是 `localhost:5173`，生产不配则前端全部被 CORS 拦。
   另：代码里生产环境写 `*` 会**降级为仅同源**（比不配更糟）。
4. **`SUPABASE_JWT_SECRET` 是多余的**：全项目零引用。令牌校验走
   `supabaseAuth.auth.getUser(token)`（anon key 调 Supabase Auth API），不做本地验签。
5. 附带：`?pgbooster=true` 拼写错误，应为 **`pgbouncer`**；且端口要配对
   （DATABASE_URL 用 6543 连接池，DIRECT_URL 用 5432 直连）。

### 关键决策
1. **构建前环境自检挂在 `prebuild`**，会阻断三类问题：VITE_ 前缀里混入
   service_role/DATABASE_URL 等敏感值（会被内联进产物）、占位符未替换、生产开着 Mock。
   逃生舱 `ALLOW_DEMO_AUTH=1`。已实测三条路径：占位符 exit=1、注入真实变量通过、
   带 service_role exit=1。
2. **`--single-transaction` 包住整个建库**：任一文件失败整体回滚，不留半套 schema。
   本项目未用 `CREATE INDEX CONCURRENTLY`（不支持事务），因此安全。
3. **Dockerfile 必须 `apk add openssl`**：Prisma 查询引擎是原生二进制依赖 libssl，
   Alpine 漏装会在**启动时**才报错，构建阶段完全看不出 —— Prisma+Alpine 最经典的坑。
4. **`CMD ["node", "dist/server.js"]` 不经 npm**：server.ts 注册了 SIGTERM 优雅退出，
   中间多一层 npm 会丢信号，滚动更新时请求被硬切断。
5. **PM2 `instances: 2` 而非 `'max'`**：每 worker 各自建 Prisma 连接池，
   实例数 × connection_limit 超 Supabase 上限就随机报 `too many clients already`。
   `kill_timeout: 15000` 必须大于应用自身 10s 的优雅退出时限。
6. **Vite 的 `VITE_` 变量优先级**：执行构建时已存在的 `process.env` 优先，
   不会被 `.env` 文件覆盖 —— 因此平台控制台配的变量能覆盖 `.env.production`。
   已实测确认（注入 process.env 后自检读到的是注入值）。
